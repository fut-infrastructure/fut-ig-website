OperationDefinition: Get performer activities

Official URL: http://ehealth.sundhed.dk/fhir/OperationDefinition/-s-get-performer-activities Version: 11.0.3
Active as of 2026-10-29 Computable Name: get-performer-activities

This operation returns the overview of the activities a given performer is expected to carry out on behalf of a given patient, within a time period and optionally filtered by EpisodeOfCare, Condition code(s) and co-existence tag(s).

It is the counterpart of $get-patient-procedures, which reports the activities the patient performs themselves. Where $get-patient-procedures excludes any activity carrying a performer other than the patient, this operation reports exactly those activities where the performer is the one given as input.

As preparation for possible future use, the input performer is declared as a Reference to a RelatedPerson, a Patient or a Practitioner, matching the allowed targets of ServiceRequest.performer. With explicit performer, the operation is prepared for possible future use where the user invoking the operation differs from the performer.

Currently, supported performer is limited to a Reference to RelatedPerson only and for invoking user of type RelatedPerson only.

The inputs, including their interdependencies, are described in the Parameters table below.

Access control

The operation is available to user type RELATED_PERSON with context.role related_person or power_of_attorney holding the CarePlan$get-performer-activities privilege. Other RELATED_PERSON roles and the PATIENT and PRACTITIONER user types are rejected. In addition, the patient parameter must equal the Patient in the caller's security context, the performer parameter must equal the caller's own RelatedPerson, and when an EpisodeOfCare is present in the security context the episodeOfCare parameter must be supplied as exactly that single reference.

Output

For valid inputs, the server returns a Bundle of type collection with the following entries:

  • One Parameters resource holding the overview as rows and columns, see Rows and columns below.
  • The ServiceRequest resources referenced from the rows.
  • Possibly an OperationOutcome describing encountered warnings.

Unlike $get-patient-procedures, the Bundle carries no CarePlan resource: the performer is given the activities they are to perform and nothing further of the patient's plan. The CarePlan and PlanDefinition are still referenced on each row, so the user system can tell which activities belong to the same plan and determine seamless activity groups.

Only timeslots falling in a sub-period where the calling RelatedPerson was recorded as performer are returned, determined from the technical versions of the ServiceRequest within the requested period. Timeslots, counts and completion information belonging to another performer - including the patient themselves - are excluded from the output entirely.

Rows and columns

The Parameters resource is to be read as a table:

  • Rows: each top-level Parameters.parameter is one row, that is, one resolved timeslot (or one unresolved, ad hoc or extra activity) of a ServiceRequest. Rows are named item_1, item_2, etc. The name only distinguishes the rows from each other and carries no further meaning. The number of rows is the number of top-level parameters.
  • Columns: each Parameters.parameter.part of a row is one column of that row. The column is identified by part.name, which is one of the column names listed below, and the cell value is the part.value[x] of the type stated for the column.

A user system should look up columns by part.name rather than by position, and should expect a column to be absent from a row where it has no value (for instance ResolvedTimingStart for an Unresolved activity). Unlike $get-patient-procedures, a count of zero is reported rather than left out.

Columns

  • ServiceRequest (valueReference): Reference to the ServiceRequest.
  • ServiceRequestVersionId (valueId): The version of the ServiceRequest (version specified at time of submit-measurement or the current version (for expected activities)).
  • CarePlan (valueReference): Reference to the CarePlan the activity belongs to. The resource itself is not included in the Bundle.
  • PlanDefinition (valueReference): Reference to the plan template the CarePlan was created from. The resource itself is not included in the Bundle.
  • Activity (valueString): Description of the planned activity.
  • ResolvedTimingStart (valueDateTime): A planned start time for the activity in the requested period.
  • ResolvedTimingEnd (valueDateTime): A planned end time for the activity in the requested period. May be identical to start if no duration is specified in the measurement regime.
  • TotalSubmitted (valueInteger): The number of measurements already submitted for this ServiceRequest and resolved timing.
  • SubmittedTimely (valueInteger): The number of measurements where the measurement time matches the resolved timing.
  • TimingType (valueCodeableConcept, system http://ehealth.sundhed.dk/cs/resolved-timing-type):
    • Resolved: a measurement regime that is supported by the infrastructure and where resolved timing and requested number of measurements can be calculated.
    • Unresolved: a measurement regime that is not supported by the infrastructure. Resolved Timing Start, end, submitted timely and Occurrences requested will be empty.
    • Adhoc: A ServiceRequest without a measurement regime or a measurement regime stating ad-hoc.
    • Extra: The service request may be performed outside the resolved timing.
  • OccurrencesRequested (valueInteger): Expected number of measurements.
  • TotalInvalidated (valueInteger): Number of measurements which are invalidated.

Language: en

URL: [base]/$get-performer-activities

Parameters

UseNameScopeCardinalityTypeBindingDocumentation
INpatient1..1Reference (ehealth-patient)

The Patient whose episodes of care, plans, activities and measurement data form the basis of the overview. Must equal the Patient in the caller's security context. Must be an absolute reference, since the Patient is served by another service in the platform; a relative reference such as Patient/123 is not matched against the stored references and yields no activities.

INperformer1..1Reference (ehealth-relatedperson, ehealth-patient, ehealth-practitioner)

The person recorded as performer (ServiceRequest.performer) on the activities. Currently only RelatedPerson is supported, and it must equal the caller's own RelatedPerson. Must be an absolute reference, see patient.

INstart1..1dateTime

Start of the period of interest. Must not be after end, and must not be further back than the configured measurement age limit. A request outside this limit is rejected.

INend1..1dateTime

End of the period of interest. Must not be before start, and must not be further ahead than the configured activity horizon. A request outside this limit is rejected.

INextra1..1boolean

Set to true if rows should be included for activities flagged as extra, i.e. where measurement data may be submitted on request or on the person's own initiative. Whether the ServiceRequest is included when extra is true is based on the ServiceRequest.includeAsExtra field.

IN_tag0..*Coding

If provided, the activities considered are those carrying a co-existence tag matching at least one of the codes in the list. Can be combined with either episodeOfCare or conditionCode.

INepisodeOfCare0..*Reference (ehealth-episodeofcare)

If provided, activities must belong to a CarePlan related to one of the stated EpisodeOfCare. Mutually exclusive with conditionCode: supplying both is rejected, and supplying neither considers every episode of care of the patient. When the caller's security context names an EpisodeOfCare, this parameter is required and must be exactly that single reference. Must be absolute reference(s), see patient.

INconditionCode0..*Coding

If provided, activities must come from a CarePlan carrying one of the stated condition codes. The code is matched against the condition of the CarePlan the activity belongs to, unlike $get-patient-procedures where it is matched against the conditions of the EpisodeOfCare. Mutually exclusive with episodeOfCare: supplying both is rejected. Consequently it is not available to a caller whose security context names an EpisodeOfCare, since that caller must supply episodeOfCare; such a caller narrows the result by co-existence tag or by period instead.

OUTreturn0..1Bundle

A Bundle of type collection containing a Parameters resource with the overview rows, the ServiceRequest resources referenced from the rows and possibly an OperationOutcome describing encountered warnings. See Output and Rows and columns above for how to read the Parameters resource.
